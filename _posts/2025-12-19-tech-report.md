## 서론: 데이터베이스 설계의 초석, 정규화

안녕하세요, 여러분! IT 기술 블로거 Chaelin입니다. 오늘 우리는 데이터베이스 설계의 핵심이자 많은 개발자가 깊이 고민하는 주제인 'DB 정규화'에 대해 심층적으로 다뤄볼 예정입니다. 정규화는 데이터의 중복을 줄이고 무결성을 보장하여, 결국 안정적이고 효율적인 데이터베이스 시스템을 구축하기 위한 필수적인 과정입니다.

단순히 1차, 2차, 3차 정규형을 넘어, 데이터 모델링에서 맞닥뜨릴 수 있는 복잡한 시나리오들을 해결하기 위한 BCNF, 4NF, 5NF와 같은 고급 정규형들을 탐구하고, 때로는 성능 최적화를 위해 의도적으로 정규화를 포기하는 '비정규화' 전략까지 폭넓게 살펴보겠습니다. 자, 그럼 데이터베이스 설계의 심오한 세계로 함께 떠나볼까요?

## 본문: 정규화의 깊은 이해와 비정규화 전략

### 1. 기본 정규형 복습: 1NF, 2NF, 3NF

정규화는 데이터베이스 테이블을 여러 개의 작은 테이블로 분해하는 과정입니다. 이는 데이터 중복을 최소화하고 갱신 이상(Insertion Anomaly, Deletion Anomaly, Update Anomaly)을 방지하여 데이터의 일관성과 무결성을 확보합니다.

*   **1차 정규형 (1NF):** 테이블의 모든 컬럼이 원자값을 가져야 합니다. 즉, 하나의 컬럼에 여러 값이 존재하거나 리스트 형태로 저장되지 않아야 합니다.
*   **2차 정규형 (2NF):** 1NF를 만족하고, 기본키가 아닌 모든 컬럼이 기본키 전체에 대해 완전 함수 종속이어야 합니다. 부분 함수 종속을 제거합니다.
*   **3차 정규형 (3NF):** 2NF를 만족하고, 기본키가 아닌 컬럼 간의 이행 함수 종속(Transitive Dependency)을 제거합니다. 즉, 기본키가 아닌 어떤 컬럼이 다른 비기본키 컬럼을 결정해서는 안 됩니다.

### 2. 고급 정규형: BCNF, 4NF, 5NF

기본 정규형만으로는 해결하기 어려운 복잡한 종속성 문제들이 있습니다. 이를 해결하기 위해 더욱 엄격한 고급 정규형들이 등장합니다.

#### 2.1. 보이스-코드 정규형 (BCNF, Boyce-Codd Normal Form)

BCNF는 3NF보다 더욱 강력한 정규형입니다. 3NF가 '기본키가 아닌 모든 컬럼이 기본키 전체에 대해 완전 함수 종속'을 요구하는 반면, BCNF는 '모든 결정자가 후보키'가 되어야 합니다. 즉, 테이블 내의 모든 함수 종속성 X → Y에서 X가 반드시 후보키여야 합니다.

**BCNF가 필요한 경우 (3NF 만족, BCNF 위반 예시):**

학생이 특정 과목을 수강하고, 그 과목은 특정 교수가 가르칩니다. 이때 한 과목을 여러 교수가 가르칠 수도 있습니다.

`과목` (<u>과목코드</u>, 과목명, 담당교수, 강의실)

| 과목코드 | 과목명     | 담당교수 | 강의실 |
| :------- | :--------- | :------- | :----- |
| DB001    | 데이터베이스 | 김교수   | A101   |
| DB001    | 데이터베이스 | 이교수   | A101   |
| OS002    | 운영체제   | 박교수   | B202   |

여기서 함수 종속성은 다음과 같습니다:
*   `과목코드` → `과목명`, `강의실` (과목코드가 기본키의 일부가 될 수 있음)
*   `담당교수` → `강의실` (한 교수는 하나의 강의실에서만 수업한다고 가정)
*   `과목코드`, `담당교수` → `강의실` (이것이 후보키가 될 수 있음)

이 테이블은 3NF를 만족합니다 (이행적 종속 없음). 하지만 `담당교수`는 후보키가 아니지만 `강의실`을 결정하는 결정자입니다. 즉, `담당교수` → `강의실` 종속성 때문에 BCNF를 위반합니다.

**BCNF로 분해:**

1.  **`과목`** (<u>과목코드</u>, 과목명)
2.  **`담당_강의`** (<u>담당교수</u>, 강의실)
3.  **`과목_담당`** (<u>과목코드</u>, <u>담당교수</u>)

```sql
-- 원본 테이블 (BCNF 위반)
CREATE TABLE CourseAssignments_ViolatesBCNF (
    CourseCode VARCHAR(10) NOT NULL,
    CourseName VARCHAR(50),
    Professor  VARCHAR(50) NOT NULL,
    Classroom  VARCHAR(10),
    PRIMARY KEY (CourseCode, Professor) -- CourseCode, Professor가 후보키
);

-- BCNF 분해
CREATE TABLE Courses_BCNF (
    CourseCode VARCHAR(10) PRIMARY KEY,
    CourseName VARCHAR(50)
);

CREATE TABLE Professors_Classrooms_BCNF (
    Professor  VARCHAR(50) PRIMARY KEY,
    Classroom  VARCHAR(10)
);

CREATE TABLE Course_Professor_Assignments_BCNF (
    CourseCode VARCHAR(10),
    Professor  VARCHAR(50),
    PRIMARY KEY (CourseCode, Professor),
    FOREIGN KEY (CourseCode) REFERENCES Courses_BCNF(CourseCode),
    FOREIGN KEY (Professor) REFERENCES Professors_Classrooms_BCNF(Professor)
);
```

#### 2.2. 4차 정규형 (4NF, Fourth Normal Form)

4NF는 다치 종속성(Multi-valued Dependency, MVD)을 제거합니다. A →→ B 와 같이 A가 여러 B 값을 결정하고 B가 A에 대해 독립적일 때 다치 종속성이 존재한다고 합니다. BCNF는 함수 종속성(Functional Dependency)에만 초점을 맞추지만, 4NF는 데이터 간의 더 복잡한 관계인 다치 종속성을 다룹니다.

**4NF가 필요한 경우 (MVD 예시):**

학생이 여러 취미를 가질 수 있고, 여러 동아리에 가입할 수 있습니다. 이때 학생의 취미와 동아리는 서로 독립적입니다.

`학생_정보` (<u>학생ID</u>, 취미, 동아리)

| 학생ID | 취미   | 동아리     |
| :----- | :----- | :--------- |
| S001   | 독서   | 독서모임   |
| S001   | 독서   | 밴드동아리 |
| S001   | 운동   | 독서모임   |
| S001   | 운동   | 밴드동아리 |

여기서 `학생ID` →→ `취미` (학생ID는 여러 취미를 결정) 이고 `학생ID` →→ `동아리` (학생ID는 여러 동아리를 결정) 입니다. 취미와 동아리는 서로 독립적이므로, 이는 다치 종속성을 위반하며 4NF를 만족하지 않습니다.

**4NF로 분해:**

1.  **`학생_취미`** (<u>학생ID</u>, <u>취미</u>)
2.  **`학생_동아리`** (<u>학생ID</u>, <u>동아리</u>)

#### 2.3. 5차 정규형 (5NF, Fifth Normal Form) 또는 프로젝트-조인 정규형 (PJNF)

5NF는 조인 종속성(Join Dependency)을 제거합니다. 이는 테이블을 여러 개의 작은 테이블로 분해했을 때, 이 테이블들을 다시 조인하면 원래의 테이블이 손실 없이 복원될 수 있는 형태로 만드는 것입니다. 5NF는 현실 세계의 복잡한 비즈니스 규칙을 모델링할 때 나타나며, 실제 시스템에서는 매우 드물게 적용됩니다. 4NF까지 정규화된 테이블이라면 대부분 5NF도 만족하는 경우가 많습니다.

### 3. 비정규화 (Denormalization): 성능과 무결성의 균형

정규화는 데이터 무결성을 높이지만, 너무 많은 정규화는 조인 연산을 증가시켜 쿼리 성능 저하를 야기할 수 있습니다. 특히 읽기(Read) 작업이 압도적으로 많은 시스템에서는 비정규화를 통해 성능을 최적화할 수 있습니다.

**비정규화를 고려하는 경우:**

*   **성능 병목 현상:** 특정 쿼리가 너무 느려 사용자 경험을 저해할 때.
*   **복잡한 조인:** 여러 테이블을 자주 조인해야 하는 경우.
*   **집계 데이터:** 자주 사용되는 집계(합계, 평균 등) 결과를 미리 저장할 때.
*   **보고서 생성:** 복잡한 보고서 작성을 위해 데이터를 미리 통합할 때.

**비정규화 기법:**

*   **컬럼 중복:** 자주 조회되는 다른 테이블의 컬럼을 현재 테이블에 중복하여 저장합니다.
*   **테이블 통합:** 자주 함께 사용되는 여러 테이블을 하나의 큰 테이블로 통합합니다.
*   **요약 테이블 (Summary Table):** 원본 데이터에서 계산된 집계 값을 저장하는 테이블을 별도로 생성합니다.
*   **파생 컬럼:** 다른 컬럼의 값을 이용해 계산되는 컬럼을 미리 저장합니다.

비정규화는 데이터 중복을 허용하므로, 데이터 일관성을 유지하기 위한 추가적인 관리(트리거, 배치 작업 등)가 필요하며, 신중하게 접근해야 합니다. 성능 최적화를 위한 마지막 수단으로 고려하는 것이 일반적입니다.

## 결론: 목적에 맞는 정규화 수준 선택

데이터베이스 정규화는 시스템의 안정성과 확장성을 위한 필수적인 과정입니다. 1NF부터 BCNF, 4NF, 5NF까지 다양한 정규형을 이해하고 적용함으로써 데이터 모델의 무결성을 극대화할 수 있습니다. 그러나 완벽한 정규화만이 능사는 아닙니다. 때로는 시스템의 특성(예: 읽기 위주 트래픽)과 성능 요구사항을 고려하여 의도적인 비정규화를 선택하는 유연한 접근 방식이 필요합니다.

핵심은 애플리케이션의 요구사항과 데이터의 특성을 면밀히 분석하고, 데이터 무결성과 시스템 성능 사이에서 최적의 균형점을 찾는 것입니다. 이 글이 여러분의 데이터베이스 설계에 깊이를 더하는 데 도움이 되었기를 바랍니다.
